Юніт-тести рахуємо за запусками Surefire (`Tests run`), бо параметризований тест дає кілька незалежних результатів. Так кількість рядків у журналі збігається з підсумком Surefire.

**Чому кейси розділено саме так.** Автор усіх 51 ручного кейса (Рзяніна Валерія) і виконавець Run 1 спринта 3 (Потеряйло Вероніка) ручні кейси не виконують. Так ми уникаємо «ефекту автора», а Аудитор-опонент лишається незалежним від журналу, який перевіряє. Сценарій Selenium IDE повторює той самий інструмент і браузер, що й у спринті 4.

**Правила виконання:**
- Кожен кейс виконується наново за його кроками. Результат записується з датою, виконавцем і середовищем. Копіювати результати спринта 3 заборонено.
- Статуси: **Passed**, **Failed**, **Blocked** (кейс неможливо виконати, причину записуємо). **Skipped** у спринті 5 не використовуємо.
- Кожен Failed посилається на дефект: наявний або новий.
- Тестові дані TD-02 (свіжий користувач) беремо з суфіксом `_s5` замість `_s3`: облікові записи `_s3` уже існують. TD-01 `tzfe41_user01` лишається; якщо після скидання demo вхід не вдається, обліковий запис створюємо наново через /register з тими самими даними.
- На demo використовуємо лише вигадані дані: без навантаження, без підбору паролів, без стоп-слів у публічних коментарях.

## 2. Порядок регресії модуля

1. Звіти Surefire **v1** знімаються повторним прогоном на v1 тим самим робочим процесом, бо звіти прогону №16 спринта 4 у репозиторії не збережено.
2. Тести спринта 4 копіюються у v2 **без змін**: публічний API v2 не змінювався, `ExampleTest.java` розробників ідентичний нашому.
3. Прогін: GitHub Actions, робочий процес **«regression v1 vs v2»** (`.github/workflows/regression-v2.yml`). Він виконує один набір на v1 і v2, потім WebDriver на demo, і будує порівняння по кожному тесту.
4. Звіти зберігаються в репозиторії: `docs/sprint5/surefire-v1/`, `docs/sprint5/surefire-v2/`.
5. Порівнюємо по назвах тестів, а не за підсумковими числами. Можливі переходи v1 → v2:
   - Passed → Passed: стабільно;
   - Failed → Passed: кандидат на Verified;
   - Failed → Failed: кандидат на Reopened;
   - **Passed → Failed: регресія, новий дефект** зі словами «регресія v2» у заголовку.

## 3. Повторна перевірка дефектів

| Дефекти | Як перевіряємо | Хто перевіряє | Хто затверджує |
|---|---|---|---|
| Модуль v1: BUG-014…BUG-019 (issues #13–#18) | Тест, що виявив дефект, на v2 | Баришполь Іван | Куценко Дарʼя |
| Demo: BUG-002…BUG-013 (issues #1–#12) | Кейс-джерело дефекту на поточному demo | виконавець кейса (розділ 1) | Куценко Дарʼя |

**Життєвий цикл:**
- **Fixed** — ставимо кожному дефекту модуля v1 після передачі v2.
- **Verified → Closed** — кроки відтворення на v2 дають очікуваний результат.
- **Reopened** — на v2 той самий фактичний результат; у коментарі записуємо фактичний результат на v2.
- Дефект demo, що відтворюється, лишається **Open** з коментарем «підтверджено на v2, дата».
- Дефект demo, що не відтворюється, отримує **Closed (not reproducible)** із причиною.

Статус змінюємо лише після реального перевиконання, з датою і виконавцем у коментарі. Новий дефект реєструємо за шаблоном спринта 3 і прив'язуємо до однієї, найконкретнішої вимоги.

## 4. Метрики

Метрики рахуємо з журналу регресії, матриці простежуваності і трекера. Формули й підставлені числа — у розділі «Метрики» звіту.

| Метрика | Формула |
|---|---|
| Покриття вимог | C = вимог із ≥1 кейсом / 42 · 100 %; окремо — для 23 вимог High |
| Pass rate | PR = passed / (passed + failed) · 100 %; Blocked до знаменника не входять |
| Частка виконаних | E = (passed + failed) / 118 · 100 % |
| Розподіл дефектів | за severity і priority, окремо для відкритих |
| Щільність дефектів | дефектів розділу / вимог розділу · 10 |
| Частка автоматизації | A = автотестів / 118 · 100 % |
| Відкриті / закриті | Open + Reopened + New проти Closed |

## 5. Критерії go / no-go

| № | Критерій | Поріг | Тип | Обґрунтування порогу |
|---|---|---|---|---|
| K1 | Відкриті дефекти Blocker і Critical | 0 | безумовний | Critical-дефект означає, що ключова функція продукту (голосування, рейтинг) не працює; випуск із ним неприйнятний за будь-яких інших чисел. |
| K2 | Покриття вимог тестами | High = 100 %; загалом ≥ 80 % | умовний | Вимоги High описують ключові функції й безпеку, тож кожна з них має бути перевірена. Загальний поріг 80 % враховує, що серед відомих непокритих зі спринта 3 переважають нефункціональні вимоги: потрібне навантаження на demo (P-20), заборонено правилами стенду (S-10), або вимогу не підтверджено замовником (D-10). |
| K3 | Pass rate | ≥ 90 % | умовний | Допускаємо до 10 % Failed, якщо це дефекти Minor / Normal з пріоритетом P3, що не блокують виконання. Більша частка означає, що продукт не відповідає SRS у помітній частині перевіреного. |
| K4 | Відкриті регресійні дефекти | 0 | безумовний | Версія 2 не може бути гіршою за версію 1: регресія скасовує сенс оновлення. |
| K5 | Blocked-кейси | кожен перевиконано або виключено з причиною | умовний | Blocked не входить до pass rate, тому кожен такий кейс має бути пояснений, інакше pass rate завищений. |

**Правило рішення:**
- **go** — виконано всі критерії;
- **умовний go** — порушено рівно один умовний критерій; умова — перелік дій і дата повторної перевірки;
- **no-go** — порушено хоча б один безумовний критерій або два й більше умовних.

Висновок записується реченням виду «Рішення …, оскільки критерій Kn не виконано: <число> при порозі <поріг>».
